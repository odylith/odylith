- Bug ID: CB-203

- Status: Open

- Created: 2026-05-19

- Severity: P2

- Reproducibility: Consistent

- Type: UX

- Description: Project release-workstream cards rendered B-id links and evidence labels with Project-local chip CSS instead of the shared dashboard control primitives used by Radar and Compass. The visible result was different button shape, typography, padding, and weight for controls that should feel like the same product system.

- Impact: Operators see inconsistent control styling across Project, Radar, and Compass, which makes Odylith feel patched together and reintroduces the same UI drift that shared primitives were meant to prevent.

- Components Affected: dashboard

- Environment(s): Odylith product repo Project dashboard surface; consumer-lane generated Project tabs with release workstream cards.

- Detected By: Operator visual review of generated Project dashboard screenshots compared with Radar and Compass chip/button styling.

- Failure Signature: Project workstream cards used local .project-job-workstream and .project-job-card em styling for B-id links and status labels rather than shared dashboard_ui_primitives-generated classes.

- Trigger Path: Open any Project tab that renders the proposed release workstream cards, then compare B-id and evidence chips with Radar or Compass workstream controls.

- Ownership: Dashboard shared UI primitives and Project intelligence presenter.

- Timeline: Captured after the Project tab showed B-id and evidence chips with local styling that did not match Radar or Compass.

- Blast Radius: Project tab release workstream cards, generated dashboard bundle, and future consumer greenfield Project surfaces that render B-id links or evidence labels.

- SLO/SLA Impact: Operator comprehension and product polish regression; no runtime availability impact.

- Data Risk: No data loss; visual inconsistency and repeated styling drift risk.

- Security/Compliance: No direct security or compliance exposure identified.

- Invariant Violated: Human-visible dashboard controls must reuse shared primitives for button and chip shape, typography, weight, padding, interaction affordance, and focus treatment.

- Workaround: None acceptable beyond patching Project to consume the shared primitive classes; manual per-surface restyling would repeat the failure.

- Root Cause: Project tab had local chip selectors and em-based status markup that duplicated styling already owned by dashboard_ui_primitives.

- Solution: Render Project B-id links through a project-workstream-chip class generated by surface_workstream_button_chip_css, render passive evidence labels through project-label-chip classes generated by detail_label_chip_css, and remove the Project-local chip box model.

- Rollback/Forward Fix: Forward fix only; reverting to Project-local chip CSS would preserve the drift.

- Verification: PYTHONPATH=src python3 -m pytest -q tests/unit/runtime/test_project_intelligence.py

- Prevention: Add tests that Project CSS includes shared primitive-derived chip classes and rejects Project-local em and nth-child chip styling.

- Agent Guardrails: Before adding a new dashboard chip, button, or B-id control, inspect dashboard_ui_primitives first and compose from the shared helper unless a new shared primitive is required.

- Preflight Checks: Check Project, Radar, Compass, Registry, Atlas, and Casebook surfaces for chip/button consistency before claiming dashboard polish.

- Regression Tests Added: tests/unit/runtime/test_project_intelligence.py asserts Project workstream chips and passive labels consume shared primitive classes and bans local em/nth-child selectors.

- Monitoring Updates: Watch visual regression screenshots for Project release workstream cards and cross-surface chip/button drift.
