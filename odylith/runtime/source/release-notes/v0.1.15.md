# Greenfield Governance and Consumer Trust Hardening

Odylith v0.1.15 is a trust-hardening release for the first thirty minutes of a
consumer repo. The release focuses on the paths where v0.1.14 exposed the most
pain: greenfield proposal apply, generated surface freshness, install/upgrade
recovery, Compass brief fallback, Atlas readability, and host-facing startup
copy.

The main product goal is simple. When Odylith creates or migrates governance
truth, Radar, Registry, Atlas, Casebook, and Compass should agree quickly, show
the same target release, and avoid making operators debug generated caches,
missing wave topology, stale dashboard versions, or internal control-plane
language.

## Greenfield Governance

Greenfield proposal apply is now treated as a flagship governance workflow, not
as a thin backlog generator.

- Accepted proposals are run through a bounded proposal Tribunal before apply,
  so structural gaps are caught before durable governance is written.
- Greenfield output now carries a clearer program shape with release targets,
  execution waves, child workstream topology, planned Registry components,
  validation obligations, and Atlas topology.
- Proposed waves are preserved instead of silently disappearing when child
  token overlap is weak. A wave with no resolved children is treated as a
  structural signal that needs explicit handling, not as disposable text.
- Greenfield consumer projects default the first release target to `0.0.1`
  unless the operator supplies another release selector.
- Apply and authoring paths refresh owned surfaces so Radar and Compass show the
  created release/program/wave state without relying on a manual browser
  refresh.
- The greenfield skill and proposal renderer now emphasize host-model-agnostic
  authorship, source evidence tiers, validation gates, assumptions, risks, and
  topology links.

## Radar, Compass, Programs, Waves, And Releases

v0.1.15 tightens the release-planning spine that connects backlog, programs,
waves, and dashboard state.

- `release-0-1-15` is the active v0.1.15 release target and is projected into
  Radar and Compass as `0.1.15`.
- v0.1.15 targeting is intentionally narrow: only branch-owned hardening
  workstreams are assigned to this release, while older release workstreams keep
  their original target history and remain filterable under their prior
  releases.
- Current-release alias changes never imply bulk retargeting. Workstreams move
  only through explicit per-workstream assignment, and completed prior-release
  work remains attached to the release where it completed.
- Program and wave authoring gained CLI paths for adoption and assignment so
  operators are not forced to hand-edit governed front matter to satisfy
  reciprocal topology validators.
- `backlog create` can attach new children to an umbrella workstream through a
  supported CLI path.
- Wave and program help now forwards the real backend command contract instead
  of showing wrapper-only arguments.
- Compass release target cards no longer make the empty card body clickable.
  Only explicit buttons navigate.
- Compass wave labels, dependency labels, progress labels, and current
  workstream rows have tighter fit behavior so labels do not bleed into adjacent
  cards or columns.

## Compass Standup Brief Recovery

Compass now treats narration failure as status metadata, not as a reason to
erase useful brief content.

- If fresh narration fails, Compass keeps the last ready standup brief visible.
- The failure state is moved into the header status line instead of replacing
  the Standup Brief body with a large warning card.
- Status copy is concise but descriptive. It distinguishes cases such as
  provider failure, unreachable provider, timeout, rate or budget limits,
  unusable narration, and validation failure.
- The status line remains layout-safe even when it is combined with stale
  snapshot notices.
- Browser tests cover same-window fallback, retained history fallback, warning
  status, copy behavior, and overflow prevention.

## Install, Upgrade, And Migration

Existing installs should now feel like upgrades, not repeated first installs.

- Hosted install and direct install paths detect existing Odylith trees and run
  the upgrade and migration path.
- Upgrade/migration now refreshes the dashboard afterward so the rendered shell
  version catches up with the authoritative installed version.
- Fallback install state cleanup no longer drops the release spotlight for the
  newly installed or upgraded release.
- Non-git project folders no longer show the large recurring Git-missing notice
  on every refresh. Odylith still records reduced repo intelligence internally,
  but it does not block the surface with a modal-style warning.
- Historical migration coverage includes generated dashboard assets, release
  targets, Atlas render style, Casebook metadata, and bundle mirrors.
- v0.1.15 is migration-marked. Upgrades from `0.1.10`, `0.1.11`, `0.1.12`,
  `0.1.13`, and `0.1.14` route through the registered
  `v0.1.15-atlas-box-explanation-contract` migration before release activation.

## Sync And Generated Surface Freshness

The generated surface pipeline now treats stale success as a release-blocking
failure class.

- Generated refresh guards use stronger content freshness checks so same-size
  source edits cannot be mistaken for unchanged inputs.
- `dashboard refresh --force` can bypass stale guard state for targeted surface
  recovery.
- `odylith sync --force` was hardened for lower-latency recovery after upgrade
  and migration.
- Sync output and dirty-overlap handling now prefer the narrowest successful
  repair path when the problem is generated dashboard drift.
- Radar traceability graphs now carry a content-backed source fingerprint and
  are rebuilt before Radar render when release, program, backlog, Registry, or
  Atlas source truth changes.
- Release assignment event logs are first-class Radar sync inputs, so selective
  sync no longer skips release-target changes that only touch
  `odylith/radar/source/releases/`.
- Governed sync action results now use one structured result contract across
  dashboard refresh and full sync execution, preventing successful action steps
  from crashing during result coercion.
- Registry, Radar, Casebook, Atlas, and Compass authoring paths can trigger
  owned-surface refreshes instead of waiting for a broad manual sync.
- Surface render batching reduces avoidable repeated work during governed
  refreshes.

## Atlas Diagram Readability

Atlas visual rendering now has a deterministic readability grammar.

- Authored Mermaid styling still wins when a diagram already declares explicit
  styling.
- Renderer-owned default styling colors nodes by semantic label buckets and
  uses lighter container washes for groups.
- Diagram containers are intentionally lighter than their inner nodes so
  grouping is visible without turning the canvas into a colored background.
- The viewer stage stays clean white, without ruled or gradient backgrounds.
- Historical SVG and PNG artifacts can be rerendered during migration when the
  Atlas render-style fingerprint changes.
- Generated Atlas detail views now explain every Mermaid flowchart container
  and every visible box inside those containers. Catalog-authored explanations
  can override the generated copy, but they must be clear complete sentences.
- Browser and render tests cover color/style freshness and layout readability.

## Casebook Reliability

Casebook received trust fixes for governed bug memory and rendered detail UX.

- Casebook status and type handling moved toward controlled lifecycle metadata
  and human-readable display labels instead of leaking internal tokens as UI
  copy.
- Detail summaries render in a full-width `Summary` box after the labels and
  source controls.
- Stale query/filter state is treated as UI state to normalize or discard,
  rather than as a reason to show an empty list while claiming all filters are
  clear.
- Release closeout logic was hardened so fixed-pending-release bugs can be
  resolved when their target release ships.
- New Casebook records capture the v0.1.15 stabilization bugs around greenfield
  topology, stale generated surfaces, dashboard drift, install upgrade
  behavior, Atlas readability, Compass label overflow, and non-git onboarding
  noise.

## Benchmark Interpretation Contract Documentation

The benchmark interpretation contract was moved and repaired so GitHub renders it
cleanly.

- The interpretation contract now lives under `docs/research/`.
- README and docs links point at the new research location.
- GitHub-hostile math macro usage was removed or rewritten.
- Unit tests guard against unsupported macro patterns and malformed display math
  in the benchmark formal-model document.

## Host-Model Agnostic Startup

v0.1.15 keeps the engines active while making host-facing startup less noisy.

- Startup output is summarized through host-agnostic status text instead of
  dumping control-plane packets into ordinary chat.
- Codex and Claude session-brief paths share the same product contract without
  making Casebook, Compass, or startup behavior Claude-specific.
- Context Engine, Execution Engine, Tribunal, Intervention, Discipline, memory,
  topology, governance, and surface DAG contracts remain active. The release
  optimizes presentation, caching, batching, and routing instead of turning
  engines off.
- New tests cover Codex and Claude host session summaries plus the shared
  startup-summary helper.

## Validation

The v0.1.15 branch adds or updates coverage across:

- greenfield proposal quality, Tribunal scoring, wave preservation, release
  targeting, and topology traceability;
- generated refresh guard content fingerprints and forced refresh behavior;
- Radar traceability source fingerprints, release-event selective sync, and
  structured governed-sync action results;
- sync CLI compatibility and lower-latency generated surface recovery;
- program and wave authoring, adoption, and help forwarding;
- Compass browser behavior for release cards, workstream rows, brief fallback,
  status-line overflow, and retained history briefs;
- Atlas migration and rendered diagram style freshness;
- Casebook release closeout and detail rendering;
- install lifecycle, runtime tree policy, hosted fallback, and dashboard refresh
  after upgrade;
- benchmark interpretation contract documentation rendering rules.

v0.1.15 is therefore less about adding a single new surface and more about
making Odylith's existing governance promise harder to break: source truth,
generated dashboards, migration behavior, release targeting, and host-facing
guidance should now line up faster and fail more honestly when they cannot.
